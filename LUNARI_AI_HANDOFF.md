# Lunari — постоянная инструкция для ChatGPT / будущих чатов

> Этот файл нужен, чтобы в новом чате не восстанавливать рабочий процесс с нуля. Перед любыми изменениями Lunari сначала прочитать этот файл, затем проверить актуальное состояние репозитория, веток, PR и CI.

## 1. Репозиторий и роль ChatGPT

- Репозиторий: `viktoriaboreichuk/My-friendi`.
- Android-приложение: Lunari.
- Канонический `applicationId`: `com.vega.yakor`.
- ChatGPT сам работает с репозиторием через GitHub: читает код, создаёт/обновляет ветки, вносит изменения, запускает/проверяет сборки, исправляет падения CI и выдаёт пользователю готовый APK.
- Не перекладывать на пользователя ручное редактирование кода, Gradle, GitHub Actions или веток, если это можно сделать через доступные инструменты.
- Пользователь предпочитает делать изменения небольшими пакетами: одна группа UI/функциональных правок → сборка → установка → проверка на телефоне → следующая группа правок.

## 2. Главное правило обновлений APK

Обычные тестовые версии Lunari должны устанавливаться **поверх уже установленного приложения**, а не рядом с ним.

Поэтому:

- не менять `applicationId`;
- не добавлять `applicationIdSuffix` для обычных пользовательских тестов;
- не создавать `.stage`, `.test`, `.dev`-пакеты без прямой просьбы пользователя;
- `versionCode` каждой новой версии должен быть больше предыдущего;
- APK должен быть подписан **тем же постоянным ключом**, которым подписаны предыдущие устанавливаемые версии;
- перед выдачей APK проверять совпадение сертификата подписи с предыдущей рабочей APK, если есть хоть малейшее сомнение.

Если Android пишет «конфликт с другим пакетом» или не разрешает обновление поверх — сначала проверять package name и сертификат подписи. Не предлагать удалять старое приложение как стандартное решение, потому что это может удалить пользовательские данные.

## 3. Постоянная подпись Android

Постоянный signing key существует и уже использовался для версий, которые ставились поверх друг друга.

- Сам ключ **не хранится в GitHub** и не должен туда попадать.
- Не просить пользователя присылать ключ, пароль или содержимое keystore текстом в чат.
- Приватный резервный архив называется `Lunari-signing-backup-KEEP-PRIVATE.zip` и хранится вне репозитория в приватном файловом хранилище пользователя / ChatGPT Library.
- При необходимости использовать этот резервный архив для локальной подписи готового APK вне GitHub.
- Не публиковать alias, пароли, приватные ключи, содержимое keystore или другие секреты в коде, PR, issue, логах или сообщениях.
- После окончания разработки пользователь хочет получить отдельный приватный архив ключей и короткую инструкцию по хранению.

Перед выдачей обновления:

1. Убедиться, что APK имеет `applicationId = com.vega.yakor`.
2. Убедиться, что `versionCode` увеличен.
3. Подписать постоянным Lunari key.
4. Сравнить сертификат подписи с предыдущей рабочей APK.
5. Только после этого дать пользователю ссылку и явно сказать, что APK ставится поверх существующей Lunari.

## 4. Git / ветки / PR

Рабочая схема:

- для новой версии использовать отдельную рабочую ветку;
- держать PR черновиком, пока пользователь визуально/функционально не одобрил версию;
- не считать релиз финальным только потому, что CI зелёный;
- не merge в `main` без явного подтверждения пользователя, что текущая версия принята;
- после принятия версии обновить раздел «Текущее состояние» в этом файле.

Если в новом чате пользователь говорит «иди в плагин», «зайди в репозиторий», «продолжай сборку» и т.п. — не объяснять, что нужен код или архив. Сначала проверить GitHub-доступ и этот репозиторий, затем продолжить работу самостоятельно.

## 5. CI / сборка

- Основной workflow: `.github/workflows/build-apk.yml`.
- Не говорить «готово», пока не проверены последние GitHub Actions jobs.
- Красный крест = сначала открыть шаг и логи, определить конкретную причину, исправить, запустить новый прогон.
- Сам факт `BUILD SUCCESSFUL` внутри Gradle ещё не означает, что весь workflow зелёный: отдельно проверять verify/upload steps.
- После зелёного прогона скачать artifact, подготовить пользовательский APK, подписать постоянным ключом и проверить подпись.
- Пользователю отдавать непосредственно `.apk`, а не заставлять его разбираться с GitHub artifact ZIP.

## 6. UI-процесс

Пользователь сначала обсуждает дизайн и визуальные референсы в чате, затем утверждённые изменения переносятся в код.

При реализации:

- строго сохранять элементы, которые пользователь явно сказал не менять;
- не «улучшать заодно» соседние элементы без согласования;
- если пользователь просит изменить только карточки — не менять круглые изображения, их рамки, фон, навигацию и т.п.;
- после каждой небольшой группы правок делать APK для проверки на реальном телефоне;
- скриншот с телефона является главным источником для следующей итерации.

## 8. Что делать в начале нового чата

Если пользователь говорит, что продолжает Lunari:

1. Открыть `LUNARI_AI_HANDOFF.md`.
2. Проверить доступ к `viktoriaboreichuk/My-friendi`.
3. Проверить актуальные ветки и открытые PR.
4. Проверить последний commit/CI активной ветки.
5. Сверить номер текущей версии и `versionCode`.
6. Только после этого продолжать с последней точки — не заставлять пользователя пересказывать историю разработки.

Если содержимое этого файла расходится с более свежим состоянием GitHub или прямой инструкцией пользователя, приоритет имеет более свежее состояние GitHub и текущая инструкция пользователя; затем этот файл нужно обновить.
